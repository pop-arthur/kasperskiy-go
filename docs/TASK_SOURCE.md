Это тестовое задание от Kaspersky на разработку Backend-сервиса. По сути, тебе нужно реализовать небольшой REST API, который хранит информацию о компьютерных угрозах (вирусах, троянах и т. д.) и позволяет получать, добавлять и обновлять её.

Само задание несложное, но в нём есть пространство, чтобы показать знание архитектуры, баз данных, тестирования и безопасности.

## 1. Что именно нужно сделать

Представь, что у Kaspersky есть база вредоносных файлов. Каждый файл идентифицируется по его MD5-хешу — строке из 32 шестнадцатеричных символов.

Например:

```
{
  "md5": "d41d8cd98f00b204e9800998ecf8427e",
  "name": "Trojan.Win32.Generic"
}
```

Тебе нужно написать сервер, который умеет выполнять три операции.

| Метод  | Endpoint      | Действие                       |
| ------ | ------------- | ------------------------------ |
| `GET`  | `/info/{md5}` | Найти угрозу по хешу           |
| `POST` | `/info`       | Создать новую запись об угрозе |
| `PUT`  | `/info/{md5}` | Обновить существующую угрозу   |

Удаление, получение списка всех угроз и сканирование файлов не требуются.

## 2. Как должен работать API

GET

Получение угрозы

Клиент отправляет MD5, сервер ищет его в базе и возвращает информацию. Если запись отсутствует — `404`.

POST

Создание угрозы

Клиент отправляет MD5 и название угрозы. Сервер проверяет данные и сохраняет запись. Если такой MD5 уже существует — `409 Conflict`.

PUT

Обновление угрозы

Клиент передаёт MD5 существующей записи и новое название угрозы. Сервер обновляет запись. Если её нет — `404`.

### Какие ошибки нужно обрабатывать

| Код   | Значение                          |
| ----- | --------------------------------- |
| `200` | Успешное получение или обновление |
| `201` | Запись успешно создана            |
| `400` | Некорректный MD5 или тело запроса |
| `404` | Угроза не найдена                 |
| `409` | MD5 уже существует                |
| `500` | Внутренняя ошибка сервера         |

Ошибки должны возвращаться в формате JSON с полями `message` и `details`.

## 3. Самый важный нюанс задания

В документе есть фраза:

> Перед реализацией необходимо дополнить модель угрозы полями.

Это обязательное требование. Тебе предлагают самостоятельно спроектировать более полноценную модель угрозы, а не ограничиваться двумя полями `md5` и `name`.

Я бы предложил такую модель:

```
{
  "md5": "d41d8cd98f00b204e9800998ecf8427e",
  "name": "Trojan.Win32.Generic",
  "severity": "HIGH",
  "description": "Malicious software",
  "category": "TROJAN",
  "first_detected_at": "2026-11-05T10:00:00Z",
  "updated_at": "2026-11-05T10:00:00Z"
}
```

Здесь:

- `severity` — степень опасности: LOW, MEDIUM, HIGH, CRITICAL.
- `description` — описание угрозы.
- `category` — категория: TROJAN, VIRUS, WORM и т. д.
- `first_detected_at` — когда угроза впервые зарегистрирована.
- `updated_at` — когда запись последний раз обновлялась.

Нужно также расширить OpenAPI-спецификацию, чтобы новые поля были отражены в API. При этом можно оставить дополнительные поля необязательными для клиента и установить разумные значения по умолчанию.

## 4. Что обязательно, а что будет плюсом

| Требование                        | Статус                              |
| --------------------------------- | ----------------------------------- |
| Рабочий REST API с тремя методами | Обязательно                         |
| Расширенная модель угрозы         | Обязательно                         |
| Валидация MD5 и входных данных    | Требуется для корректной работы API |
| Unit-тесты                        | Плюс                                |
| Интеграционные тесты              | Плюс                                |
| Docker                            | Плюс                                |
| PostgreSQL или другая СУБД        | Плюс                                |
| Генерация кода по OpenAPI         | Плюс                                |
| Документация                      | Плюс                                |
| Rate limiting, TLS, авторизация   | Плюс                                |

Здесь важно: СУБД формально необязательна, но для серьёзной реализации я бы точно использовал PostgreSQL. Хранить угрозы исключительно в памяти сервера — слабое решение для такого тестового.

## 6. Как сделать тестовое сильнее

Я бы реализовал его в таком порядке:

1. API-first: взять предоставленную OpenAPI-спецификацию и расширить модель угрозы.
2. Спроектировать PostgreSQL-таблицу с уникальным MD5.
3. Реализовать три endpoint'а через Controller → Service → Repository.
4. Добавить валидацию MD5, обязательных полей и допустимых значений.
5. Реализовать единый обработчик исключений с правильными HTTP-кодами.
6. Написать unit- и интеграционные тесты, в том числе на дубликаты MD5.
7. Настроить Docker Compose для запуска приложения и PostgreSQL.
8. Добавить README с инструкцией запуска, Swagger UI и примерами запросов.

В качестве дополнительного улучшения можно реализовать rate limiting и простую API-key авторизацию.

Ещё один хороший нюанс: нормализовать MD5 к нижнему регистру, чтобы один и тот же хеш с разным регистром не создавал две записи.

Хотя критерии оценки прямо не перечислены, по формулировке задания можно предположить, что Kaspersky интересуют:

- Насколько грамотно ты проектируешь API и модель данных.
- Умеешь ли разделять ответственность между слоями приложения.
- Как обрабатываешь ошибки и нестандартные ситуации.
- Способен ли самостоятельно дополнить неполные требования.

Мой совет: не превращай это в систему из десяти микросервисов. Один качественный монолит с PostgreSQL, хорошей архитектурой, тестами, Docker и документацией будет гораздо убедительнее, чем сложная инфраструктура без необходимости.

И отдельно: я бы уделил особое внимание OpenAPI, потому что в задании прямо написано, что реализация должна строиться на предоставленном контракте. Это означает, что нельзя просто придумать собственные endpoint'ы и форматы ответов — нужно соблюдать заданные методы, структуры и HTTP-коды.
