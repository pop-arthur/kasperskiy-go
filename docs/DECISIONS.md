# Архитектурные решения

Все решения ниже зафиксированы 2026-11-05. Изменения добавлять с причинами,
сохраняя историю; статус «принято» не означает реализацию будущих слоёв.

## ADR-001 — Go и стандартная библиотека

- Решение: Go 1.27.3, stdlib net/http (план), log/slog, testing/httptest.
- Причина: явный выбор Go пользователем, три REST-операции, минимум зависимостей.
  Стабильная версия проверена по https://go.dev/dl/?mode=json на дату фиксации.
- Альтернативы: установленная Go 1.25.6; сторонний HTTP framework; Java/Spring из пересказа.
- Компромиссы: старой локальной Go нужен GOTOOLCHAIN=auto и сеть для скачивания
  1.27.3; Go module directive и Docker image фиксируют версию. Framework не нужен
  до появления обоснованного требования. Docker base tag не закреплён digest.
- Статус: принято; Go/slog применены, HTTP и тесты ещё не реализованы.

## ADR-002 — Локальное имя модуля

- Решение: module kasperski-go-test.
- Причина: адрес репозитория не предоставлен; вымышленный hosting path недопустим.
- Альтернативы: дождаться URL; придумать github.com/... — отклонено.
- Компромиссы: модуль предназначен для локальной разработки; при появлении
  реального адреса согласовать смену module/imports.
- Статус: принято.

## ADR-003 — Один сервис, слои по мере реализации

- Решение: composition root в cmd/api; будущие domain/usecase/transport/repository,
  DI через конструкторы, интерфейсы у потребителей.
- Причина: отделение правил от транспорта и хранения без инфраструктуры на вырост.
- Альтернативы: весь сервис в main; микросервисы; generic repository; DI framework.
- Компромиссы: границы пакетов потребуют проверки по конкретным сценариям;
  сейчас создан только исполняемый каркас, остальные пакеты не материализованы.
- Статус: принято как направление дальнейшей реализации.

## ADR-004 — Хранилище и расширение контракта отложены

- Решение: сначала получить OpenAPI, уточнить модель и требования к хранению;
  пока не выбирать БД, enum/default, регистр MD5 или новые API-поля.
- Причина: пересказ содержит рекомендации, оригинала контракта нет.
- Альтернативы: сразу PostgreSQL; SQLite; память; сразу принять предложенные поля.
- Компромиссы: persistence и окончательное API-проектирование остаются открытыми;
  обязательное расширение модели должно предшествовать её реализации.
- Статус: историческое решение Bootstrap; отложенные вопросы хранения и
  модели закрыты принятыми ADR-006/007 от 2026-11-05.

## ADR-005 — Минимальная конфигурация и Docker

- Решение: только LOG_LEVEL через окружение; stdlib JSON logging; multi-stage
  Docker build, CGO_ENABLED=0, scratch, UID/GID 65532; без Compose.
- Причина: сейчас нет сервера, хранилища, секретов или вспомогательных сервисов.
- Альтернативы: dotenv/config/logging packages, Alpine runtime, Compose с БД.
- Компромиссы: нет shell и CA bundle в runtime; при будущих исходящих HTTPS
  соединениях проверить необходимость сертификатов. Точка входа сейчас завершает
  работу сразу. Compose добавлять при реальной потребности.
- Статус: принято для Bootstrap; отсутствие Compose пересмотрено в ADR-008
  при добавлении PostgreSQL по запросу пользователя.


## ADR-006 — Проект базы данных v1

- Решение: использовать PostgreSQL и одну таблицу threats с md5 как первичным
  ключом; текстовые md5/name, дополнительное description и серверные
  created_at/updated_at. Подробности: [проект БД](database/README.md).
- Причина: три операции по одному идентификатору; постоянное хранение и
  конкурентная уникальность без лишних сущностей. В предоставленном описании
  требуется расширить модель; description — минимальное предметное расширение.
- Альтернативы: SQLite — проще развёртывать, но иной режим конкурентной записи;
  память — не сохраняет данные при перезапуске; бинарный MD5 — компактнее,
  но требует преобразования; отдельный surrogate id — не нужен текущему API.
- Компромиссы: PostgreSQL потребует отдельный сервис и драйвер. Нормализация
  MD5 к lowercase, дополнительные поля и семантика их обновления
  зафиксированы в контракте API 1.1.0 (ADR-007). Одного текущего md5/name
  недостаточно, чтобы считать требование расширения модели выполненным.
- Статус: предложено и затем принято пользователем 2026-11-05.
  Таблица реализована SQL-миграцией на следующем этапе 2026-11-05;
  версии PostgreSQL, драйвера и мигратора выбраны в ADR-008.
  Go-адаптер ещё не реализован.


## ADR-007 — Контракт API 1.1.0

- Решение: сохранить пути, методы, operationId и HTTP-коды исходного API;
  добавить необязательный description и обязательные readOnly даты в ответ.
  Принимать MD5 в обоих регистрах, хранить и возвращать lowercase.
  POST требует md5/name, PUT — name; PUT полностью заменяет name/description,
  отсутствие description удаляет его. Явный null не принимается.
- Причина: пользователь принял модель v1 и поручил обновить OpenAPI;
  задание требует расширения модели до реализации. Явные правила устраняют
  неоднозначность при реализации и тестировании.
- Альтернативы: обязательное description нарушает совместимость старых запросов;
  PATCH-семантика PUT сохраняла бы не переданное описание; JSON null для
  очистки потребовал бы nullable. Эти варианты не выбраны.
- Компромиссы: прежние запросы md5/name без U+0000 остаются валидными, но PUT без description
  удаляет ранее сохранённое описание. Ответ расширен; клиенты должны
  допускать дополнительные поля. Старые схемы ответов не обещали даты,
  обязательность новых полей усиливает гарантии сервера, не требования к запросам.
  Дополнительные поля запросов разрешены и игнорируются; клиентские даты
  не используются. name/description допускают пустые строки и пробелы без trim,
  без лимита длины; U+0000 запрещён из-за PostgreSQL text. Это явное уточнение
  исходного набора допустимых строк. Ошибки всегда содержат строки message/details;
  details может быть пустой, внутренние подробности не раскрываются.
- Статус: принято 2026-11-05. info.version = 1.1.0, openapi = 3.0.0.
  Актуальный контракт — backend/openapi.yaml; исходный файл сохранён
  без изменений в backend/openapi.original.yaml. Реализация ещё отсутствует.


## ADR-008 — PostgreSQL 18.6, pgx v5.12.0 и golang-migrate v4.20.1

- Решение: официальный postgres:18.6-bookworm и migrate/migrate:v4.20.1
  с фиксированными digest в Compose; native github.com/jackc/pgx/v5 v5.12.0
  с pgxpool для будущего Go-адаптера. SQL-миграции up/down в migrations;
  отдельный запуск migrate CLI, без автоматических миграций в API.
- Причина: PostgreSQL 18 — стабильная поддерживаемая ветка; 18.6 — текущий
  доступный minor на дату проверки. Фиксация patch/digest даёт воспроизводимость.
  pgx предназначен для PostgreSQL, написан на Go и включает пул; v5.12.0
  требует Go >= 1.25, совместим с выбранной Go 1.27.3. Эта версия включает
  исправления безопасности относительно 5.11.0. В go.mod будет добавлен
  вместе с первым использующим его кодом, а не как неиспользуемая зависимость.
  golang-migrate выполняет обычный SQL и ведёт версию/dirty-флаг; не требует
  собственных Go-миграций или подключения мигратора к бизнес-коду.
- Альтернативы: PostgreSQL 17 — поддерживается, но нет причины начинать с
  предыдущей ветки; PostgreSQL 19 RC — не стабильный релиз; latest — меняется
  без явного обновления проекта. Alpine — компактнее, но размер образа БД
  сейчас не приоритет; выбран Debian bookworm. database/sql + pgx stdlib
  добавил бы ненужный сейчас интерфейс; ORM не нужен для трёх операций.
  Goose также подходит, но SQL up/down golang-migrate достаточен;
  initdb-скрипты выполняются только на пустом томе и не заменяют миграции.
- Компромиссы: образы нужно обновлять явно вместе с digest и проверками.
  Мигратор содержит собственный PostgreSQL-драйвер; он изолирован от
  будущего pgx-драйвера приложения. PostgreSQL требует отдельный контейнер.
  Down первой миграции удаляет таблицу и данные. schema_migrations —
  техническая таблица инструмента, не новая предметная сущность.
  Локальная роль из POSTGRES_USER создаётся образом как административная;
  отдельную роль приложения определить при его подключении.
- Статус: принято и проверено 2026-11-05. Миграция и Compose реализованы;
  На этапе repository layer драйвер добавлен в go.mod (ADR-010);
  cmd/api пока не создаёт пул и не подключается к БД.

Источники выбора версий и поведения:

- [Поддерживаемые версии PostgreSQL](https://www.postgresql.org/support/versioning/).
- [Официальный образ PostgreSQL: теги и том для версии 18](https://hub.docker.com/_/postgres).
- [pgx README: native interface и pgxpool](https://github.com/jackc/pgx).
- [pgx changelog v5.12.0](https://github.com/jackc/pgx/blob/v5.12.0/CHANGELOG.md);
  версия и требование Go также проверены через go list -m -json github.com/jackc/pgx/v5@v5.12.0.
- [golang-migrate v4.20.1](https://github.com/golang-migrate/migrate/releases/tag/v4.20.1)
  и [команды CLI](https://github.com/golang-migrate/migrate/tree/v4.20.1/cmd/migrate).


## ADR-009 — Минимальный контракт repository layer

- Решение: определить у потребителя internal/usecase интерфейс ThreatRepository
  из GetByMD5/Create/Update; конкретный адаптер планируется в
  internal/repository/postgres. Вход — domain.MD5 и domain.ThreatData
  (Name, Description *string), результат — domain.Threat с датами БД.
  Предусмотреть domain.ErrThreatNotFound и domain.ErrThreatAlreadyExists;
  драйверные ошибки преобразовывать внутри адаптера.
- Причина: ровно три сценария API, один ключ и одна таблица. Выделение
  изменяемых полей исключает управление датами/ключом через операции записи;
  *string сохраняет различие SQL NULL и пустого описания. Один оператор
  с RETURNING даёт результат записи без дополнительного SELECT.
- Альтернативы: универсальный CRUD/Save с upsert нарушил бы разные ошибки
  POST/PUT; Exists перед INSERT не защищает от гонки; передача полной Threat
  допускает клиентские даты; HTTP DTO или pgx-типы в контракте связывают слои.
  Отдельные Reader/Writer-интерфейсы и transaction manager пока не требуются.
- Компромиссы: методы получают уже проверенные/нормализованные данные;
  проверка входа остаётся в domain/usecase/transport. SQL-ограничения — последняя
  защита. Ошибка контекста/сети при записи не гарантирует, что запись не произошла;
  автоматические повторы и exactly-once не обещаются. Native pgx остаётся
  деталью адаптера; жизненным циклом пула управляет composition root.
- Статус: контракт определён 2026-11-05 по запросу пользователя;
  [спецификация](backend/REPOSITORY.md) сохранена. На следующем этапе
  Go-типы, интерфейс и адаптер реализованы и проверены (ADR-010).


## ADR-010 — Реализация repository layer на pgx

- Решение: реализовать согласованный контракт тремя пакетами: internal/domain
  (MD5/ThreatData/Threat, ParseMD5, Validate и ошибки), internal/usecase
  (интерфейс ThreatRepository), internal/repository/postgres (адаптер).
  NewThreatRepository принимает готовый *pgxpool.Pool; три метода выполняют
  по одному параметризованному SQL-запросу, общий scanThreat преобразует
  description и UTC-время. Ожидаемые ошибки маппятся по ErrNoRows и
  SQLSTATE/имени threats_pkey; технические причины сохраняются через %w.
- Причина: это минимальные зависимости для самостоятельного слоя хранения.
  Предусловия валидации определены в ADR-009; доменная проверка необходима
  будущему вызывающему коду, но не дублируется внутри адаптера. Серверные
  даты и RETURNING исключают дополнительное чтение после записи.
- Альтернативы: интерфейс пула ради SQL-моков, общий базовый repository,
  ORM, transaction manager и скрытые retry не нужны текущим операциям.
  Вместо них выбраны тесты настоящего адаптера на PostgreSQL с реальной миграцией.
- Компромиссы: поля доменных структур экспортированы; MD5 — именованная строка,
  поэтому вызывающий код обязан использовать ParseMD5/ThreatData.Validate,
  а не unchecked cast. NULL описания представлен *string. Адаптер не читает
  env, не создаёт/закрывает пул, не выполняет миграции и не логирует ошибки.
  Ошибка отмены запроса не доказывает rollback на сервере; интеграционная
  проверка блокировки подтвердила этот случай, поэтому гарантии не усилены.
- Тестирование: domain unit tests; Go integration tests с тегом integration
  на отдельной PostgreSQL, миграцией и -race через make test-repository.
  Проверяются конкурентные Create/Update, NULL, даты, not found/duplicate,
  разные ограничения, закрытый пул, canceled/deadline и отмена во время SQL.
  Обычный go test ./... не требует БД; тестовые зависимости-моки не добавлены.
- Статус: реализовано 2026-11-05 по запросу пользователя. API, сценарии
  usecase и подключение пула в cmd/api остаются следующими этапами.
