# Архитектурные решения

Все решения ниже зафиксированы 2026-11-05. Изменения добавлять с причинами,
сохраняя историю; статус «принято» не означает реализацию будущих слоёв.

## ADR-001 — Go и стандартная библиотека

- Решение: Go 1.27.3, stdlib net/http (план), log/slog, testing/httptest.
- Причина: явный выбор Go пользователем, три REST-операции, минимум зависимостей.
  Стабильная версия проверена по https://go.dev/dl/?mode=json на дату фиксации.
- Альтернативы: установленная Go 1.25.6; сторонний HTTP framework; Java/Spring из пересказа.
- Компромиссы: старой локальной Go нужен GOTOOLCHAIN=auto и сеть для скачивания
  1.27.3; Go module directive и Docker image фиксируют версию. Framework не нужен
  до появления обоснованного требования. Docker base tag не закреплён digest.
- Статус: принято; Go/slog применены, HTTP и тесты ещё не реализованы.

## ADR-002 — Локальное имя модуля

- Решение: module kasperski-go-test.
- Причина: адрес репозитория не предоставлен; вымышленный hosting path недопустим.
- Альтернативы: дождаться URL; придумать github.com/... — отклонено.
- Компромиссы: модуль предназначен для локальной разработки; при появлении
  реального адреса согласовать смену module/imports.
- Статус: принято.

## ADR-003 — Один сервис, слои по мере реализации

- Решение: composition root в cmd/api; будущие domain/usecase/transport/repository,
  DI через конструкторы, интерфейсы у потребителей.
- Причина: отделение правил от транспорта и хранения без инфраструктуры на вырост.
- Альтернативы: весь сервис в main; микросервисы; generic repository; DI framework.
- Компромиссы: границы пакетов потребуют проверки по конкретным сценариям;
  сейчас создан только исполняемый каркас, остальные пакеты не материализованы.
- Статус: принято как направление дальнейшей реализации.

## ADR-004 — Хранилище и расширение контракта отложены

- Решение: сначала получить OpenAPI, уточнить модель и требования к хранению;
  пока не выбирать БД, enum/default, регистр MD5 или новые API-поля.
- Причина: пересказ содержит рекомендации, оригинала контракта нет.
- Альтернативы: сразу PostgreSQL; SQLite; память; сразу принять предложенные поля.
- Компромиссы: persistence и окончательное API-проектирование остаются открытыми;
  обязательное расширение модели должно предшествовать её реализации.
- Статус: историческое решение Bootstrap; отложенные вопросы хранения и
  модели закрыты принятыми ADR-006/007 от 2026-11-05.

## ADR-005 — Минимальная конфигурация и Docker

- Решение: только LOG_LEVEL через окружение; stdlib JSON logging; multi-stage
  Docker build, CGO_ENABLED=0, scratch, UID/GID 65532; без Compose.
- Причина: сейчас нет сервера, хранилища, секретов или вспомогательных сервисов.
- Альтернативы: dotenv/config/logging packages, Alpine runtime, Compose с БД.
- Компромиссы: нет shell и CA bundle в runtime; при будущих исходящих HTTPS
  соединениях проверить необходимость сертификатов. Точка входа сейчас завершает
  работу сразу. Compose добавлять при реальной потребности.
- Статус: принято.


## ADR-006 — Проект базы данных v1

- Решение: использовать PostgreSQL и одну таблицу threats с md5 как первичным
  ключом; текстовые md5/name, дополнительное description и серверные
  created_at/updated_at. Подробности: [проект БД](database/README.md).
- Причина: три операции по одному идентификатору; постоянное хранение и
  конкурентная уникальность без лишних сущностей. В предоставленном описании
  требуется расширить модель; description — минимальное предметное расширение.
- Альтернативы: SQLite — проще развёртывать, но иной режим конкурентной записи;
  память — не сохраняет данные при перезапуске; бинарный MD5 — компактнее,
  но требует преобразования; отдельный surrogate id — не нужен текущему API.
- Компромиссы: PostgreSQL потребует отдельный сервис и драйвер. Нормализация
  MD5 к lowercase, дополнительные поля и семантика их обновления
  зафиксированы в контракте API 1.1.0 (ADR-007). Одного текущего md5/name
  недостаточно, чтобы считать требование расширения модели выполненным.
- Статус: предложено и затем принято пользователем 2026-11-05.
  Схема документирована, не реализована. Выбор версии PostgreSQL, драйвера
  и средства миграций остаётся задачей реализации.


## ADR-007 — Контракт API 1.1.0

- Решение: сохранить пути, методы, operationId и HTTP-коды исходного API;
  добавить необязательный description и обязательные readOnly даты в ответ.
  Принимать MD5 в обоих регистрах, хранить и возвращать lowercase.
  POST требует md5/name, PUT — name; PUT полностью заменяет name/description,
  отсутствие description удаляет его. Явный null не принимается.
- Причина: пользователь принял модель v1 и поручил обновить OpenAPI;
  задание требует расширения модели до реализации. Явные правила устраняют
  неоднозначность при реализации и тестировании.
- Альтернативы: обязательное description нарушает совместимость старых запросов;
  PATCH-семантика PUT сохраняла бы не переданное описание; JSON null для
  очистки потребовал бы nullable. Эти варианты не выбраны.
- Компромиссы: прежние запросы md5/name без U+0000 остаются валидными, но PUT без description
  удаляет ранее сохранённое описание. Ответ расширен; клиенты должны
  допускать дополнительные поля. Старые схемы ответов не обещали даты,
  обязательность новых полей усиливает гарантии сервера, не требования к запросам.
  Дополнительные поля запросов разрешены и игнорируются; клиентские даты
  не используются. name/description допускают пустые строки и пробелы без trim,
  без лимита длины; U+0000 запрещён из-за PostgreSQL text. Это явное уточнение
  исходного набора допустимых строк. Ошибки всегда содержат строки message/details;
  details может быть пустой, внутренние подробности не раскрываются.
- Статус: принято 2026-11-05. info.version = 1.1.0, openapi = 3.0.0.
  Актуальный контракт — backend/openapi.yaml; исходный файл сохранён
  без изменений в backend/openapi.original.yaml. Реализация ещё отсутствует.
