Дата: 2026-11-05. Статус: схема v1 принята пользователем для последующей реализации (ADR-006).

Источники: [описание задания](../TASK_SOURCE.md),

## Основание: исходный контракт и согласованное расширение

- Сервис хранит одну запись об угрозе для каждого уникального MD5.
- `ThreatCreateRequest` требует строки `md5` и `name`.
- MD5 соответствует `^[a-fA-F0-9]{32}$`: верхний и нижний регистр допустимы.
- `ThreatUpdateRequest` требует только строку `name`; MD5 приходит в пути.
  PUT «заменяет информацию о существующей угрозе», не создаёт её.
- Исходная спецификация возвращает ThreatResponse с md5/name без required.
  В API 1.1.0 обязательны md5/name/created_at/updated_at; description необязателен.
- В схемах запросов нет `minLength`/`maxLength` для name. Наличие поля
  обязательно, но запрет пустой строки или строки из пробелов не задан.
- Уникальность name не требуется. У двух разных MD5 может быть одинаковое имя.
- `ErrorResponse.message` и `details` — строки; их хранение в таблице угроз
  не требуется. В API 1.1.0 оба поля обязательны; details может быть пустой строкой.
- Требование расширить модель отражено в актуальной OpenAPI: description
  и серверные created_at/updated_at. Исходник сохранён в ../backend/openapi.original.yaml.

## Принятые решения для v1

PostgreSQL выбран для постоянного хранения и обеспечения уникальности
при конкурентных запросах. Это проектный выбор, а не требование OpenAPI;
версии выбраны в ADR-008: PostgreSQL 18.6-bookworm, native pgx/v5 v5.12.0
для адаптера и golang-migrate v4.20.1 для SQL-миграций.
Альтернативы и ограничения описаны в [ADR-006](../DECISIONS.md#adr-006--проект-базы-данных-v1).

Одна таблица `threats`, без связей и справочников. MD5 служит естественным
первичным ключом: все операции адресуют запись по нему, дополнительный id
не нужен. MD5 здесь идентификатор из контракта, не гарантия отсутствия
криптографических коллизий и не средство проверки безопасности файла.

Принятое предметное расширение модели — `description`. Служебные
`created_at`/`updated_at` позволяют отличать создание записи от её обновления.
Все три поля добавлены в OpenAPI 1.1.0; даты доступны только в ответах.
severity/category требуют согласования классификаторов; first_detected_at
нельзя подменять временем создания записи. В v1 они пока не предлагаются.

## Структура таблицы threats

| Поле | PostgreSQL-тип | NULL / default | Назначение и основание |
| --- | --- | --- | --- |
| `md5` | `text COLLATE "C"` | NOT NULL, без default | PRIMARY KEY; 32 lowercase hex-символа; поле из OpenAPI, lowercase — принятая нормализация |
| `name` | `text` | NOT NULL, без default | Имя из обязательного поля запроса; без произвольного ограничения длины и UNIQUE |
| `description` | `text` | NULL, по умолчанию NULL | Дополнительное описание; NULL означает, что описание не задано |
| `created_at` | `timestamptz` | NOT NULL, CURRENT_TIMESTAMP | Серверное время создания записи; неизменно при PUT |
| `updated_at` | `timestamptz` | NOT NULL, CURRENT_TIMESTAMP | Серверное время последнего успешного PUT; при создании равно created_at |

Текстовый MD5 проще сопоставлять с JSON и диагностировать, чем бинарные
16 байт. `text` с CHECK обеспечивает точную форму без дополнения пробелами,
характерного для `char(n)`. Ограничение размера HTTP-тела и допустимые
значения строк нужно согласовать отдельно; `text` не означает неограниченный
размер запроса. Типы PostgreSQL имеют собственные технические ограничения,
в частности text не хранит нулевой символ. OpenAPI запрещает U+0000
в name/description: такие запросы должны давать 400 до обращения к БД.

Проверять MD5 по исходному pattern, затем приводить ASCII A–F
к нижнему регистру во всех трёх операциях. В БД хранится только канонический
ключ; верхний регистр в запросах продолжает приниматься. Это предотвращает
две записи одного хеша в разном регистре. Возврат канонического MD5 вместо
исходного написания закреплён в OpenAPI 1.1.0.

## DDL и миграции

Актуальная схема — в migrations/000001_create_threats.up.sql,
откат — в migrations/000001_create_threats.down.sql. Миграции проверены
на PostgreSQL 18.6; ниже та же структура:

```sql
CREATE TABLE public.threats (
    md5 text COLLATE "C" NOT NULL,
    name text NOT NULL,
    description text,
    created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT threats_pkey PRIMARY KEY (md5),
    CONSTRAINT threats_md5_format_check CHECK (md5 ~ '^[a-f0-9]{32}$')
);
```

Единственный индекс v1 создаётся первичным ключом; отдельный UNIQUE(md5)
или второй индекс md5 избыточен. Поиска по name, фильтрации и списка в API
нет, поэтому индексы по name, датам и description пока не нужны.
Автоматических триггеров нет: DEFAULT не обновляет updated_at при UPDATE;
адаптер задаёт его явно в том же SQL-операторе.
Поведение PRIMARY KEY/CHECK описано в [документации PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html),
особенности text/char — в [описании строковых типов](https://www.postgresql.org/docs/current/datatype-character.html).

## Соответствие операций API хранению

| Операция | Действие хранения | Результат для API |
| --- | --- | --- |
| GET /info/{md5} | Поиск по нормализованному первичному ключу | Запись → 200; отсутствие → 404 |
| POST /info | INSERT новой записи с RETURNING | Создание → 201; конфликт threats_pkey → 409 |
| PUT /info/{md5} | UPDATE по ключу с RETURNING; md5/created_at не меняются | Запись → 200; ни одной обновлённой строки → 404 |

Некорректные MD5/JSON/типы/обязательные поля дают 400 до обращения к БД.
Адаптер возвращает ошибки приложения, HTTP-коды формирует transport.
Нарушение конкретного ограничения уникальности при POST преобразуется в
ошибку дубликата; остальные ошибки БД не следует автоматически считать 409
или 400. Неожиданный сбой хранения соответствует 500, без SQL и реквизитов
подключения в message/details.

Предварительный SELECT не обеспечивает уникальность при двух одновременных
POST: окончательное решение принимает PRIMARY KEY при INSERT. Не применять
upsert для POST или PUT: дубликат POST не должен менять существующую запись,
отсутствующий ключ PUT не должен создавать новую.

В принятом контракте PUT выполняет полную замену name и description:
отсутствующее description сбрасывается в SQL NULL, присутствующая строка
сохраняется (включая пустую). JSON null в запросе не принимается. Эти правила отражены в OpenAPI 1.1.0.
Неизвестные поля запросов, включая клиентские даты и md5 в теле PUT,
игнорируются и не сохраняются.

Каждое создание/обновление — один атомарный SQL-оператор. В текущем контракте
нет version, ETag или условного обновления. Принята семантика последней
успешной записи: конкурентные PUT не обнаруживают потерю предыдущего
изменения. Если нужна другая гарантия, сначала расширить контракт.

Время выставляет БД; created_at и updated_at на INSERT получают один
CURRENT_TIMESTAMP. На UPDATE адаптер явно присваивает updated_at =
CURRENT_TIMESTAMP, даже если name не изменилось. CURRENT_TIMESTAMP — начало
транзакции, поэтому это техническая отметка операции, не версия записи,
не порядок коммитов и не гарантированно строго возрастающие часы.
Операции планируются короткими; UTC использовать при отображении и
сериализации. См. [семантику времени PostgreSQL](https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT).

## Связь с OpenAPI 1.1.0

- description — необязательная строка в POST/PUT; в ответе поле опускается,
  если в БД NULL. Пустая строка возвращается как пустая строка.
- created_at/updated_at — обязательные поля ответа, readOnly date-time
  (RFC 3339, UTC с суффиксом Z); клиент не управляет ими.
- Исходная спецификация сохранена в [openapi.original.yaml](../backend/openapi.original.yaml).
  Актуальный контракт — [openapi.yaml](../backend/openapi.yaml).
- Клиентские default, enum и ограничения длины не добавлены.
  name/description не обрезаются; пустые строки и пробелы разрешены.

## Проверяемые условия будущей реализации

- Два одновременных POST одного MD5: одна строка, один успех и один конфликт.
- Одинаковый MD5 в разных регистрах адресует одну запись по принятой нормализации.
- Два MD5 с одинаковым name допустимы; отсутствующий/NULL name отклоняется,
  пустая строка и пробелы допускаются контрактом v1 без trim.
- Прямая запись некорректного или uppercase MD5 нарушает CHECK; NULL нарушает NOT NULL.
- PUT отсутствующей записи ничего не создаёт; существующей — не меняет MD5/created_at.
- updated_at выставляется при PUT; GET ничего не изменяет.
- Данные переживают перезапуск приложения и БД при настроенном постоянном томе.
- Для description проверить различия отсутствующего значения,
  пустой строки и SQL NULL и соответствующую сериализацию.

Ограничения таблицы, NULL/default, повторное применение миграций,
сохранность данных после пересоздания контейнеров и up/down/up уже
проверяются через make test-db. Go-операции хранения и их ошибки проверяются через make test-repository.
Нормализация MD5 проверена domain-тестами. HTTP-семантика PUT и JSON
пока не реализованы и остаются критериями будущих тестов приложения.


## Локальный запуск и управление миграциями

Требуются Docker Compose v2 с поддержкой up --wait и работающий Docker Engine.
В корне проекта, если .env ещё не создан:

```sh
cp .env.example .env
make db-up
make migrate-up
make migrate-version
make db-shell
```

.env читает Compose. POSTGRES_DB/POSTGRES_USER по умолчанию threats;
POSTGRES_PASSWORD обязателен, пример содержит только локальный пароль.
POSTGRES_PORT по умолчанию 5432; публикация только на 127.0.0.1.
При подключении Go-приложения будут использоваться эти же значения, хост
127.0.0.1 и порт POSTGRES_PORT; код конфигурации подключения ещё не добавлен.
Сам адаптер принимает готовый пул через конструктор и окружение не читает.
В Compose мигратор обращается к postgres:5432. Пароль передаётся отдельно
через PGPASSWORD, не вставляется в URL.

make db-up запускает только БД и ждёт healthcheck. make migrate-up применяет
миграции явно; повторный запуск выдаёт no change. Версия 1 и dirty=false
хранятся в служебной public.schema_migrations. Статус dirty не исправлять
автоматическим force: сначала выяснить причину сбоя и проверить схему.

```sh
make db-down
# Только при намеренном откате: удаляет threats вместе с данными.
make migrate-down
```

db-down удаляет контейнеры и сеть, сохраняя именованный том postgres_data.
После db-up данные доступны снова; migrate-up не удаляет существующие записи.
В PostgreSQL 18 том подключается к /var/lib/postgresql; образ использует
версионный каталог данных внутри него. Изменение major требует отдельной
процедуры переноса, простая замена тега образа не является миграцией данных.
POSTGRES_DB/USER/PASSWORD используются образом при первичной инициализации;
изменение .env не меняет уже созданные роли, пароли или базу в существующем томе.

## Проверка инфраструктуры

```sh
make test-db
```

Нужен Python 3, без сторонних Python-пакетов. Проверка создаёт случайно
названный Compose-проект с отдельным томом и свободным портом. Проверяет
реальную миграцию, повторный up, ограничения, NULL/пустые значения/default,
сохранение строки и версии миграции после down/up, откат и повторное
применение. В finally удаляет только тестовый проект и его том. Локальный
.env и данные обычной БД не используются. Это проверка SQL и инфраструктуры,
а не интеграционный тест пока отсутствующего API.
