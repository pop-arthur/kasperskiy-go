# Kaspersky Threat Service

Небольшой REST API для хранения информации об угрозах. Запись определяется по MD5: её можно добавить, получить или обновить.

Сервис написан на Go. HTTP работает на `net/http`, логи пишутся через `slog`, подключение к PostgreSQL — через `pgx`. Настройки читает `cleanenv`, миграции выполняет `golang-migrate`. HTTP-модели генерируются из OpenAPI через `oapi-codegen`, SQL-запросы — через `sqlc`.

## Запуск через Docker

1. Запустите Docker Desktop и дождитесь, пока Docker будет готов.
2. Откройте терминал в корне проекта — в папке, где лежат `Makefile` и `compose.yaml`.
3. Если `.env` ещё не заполнен, выполните [настройку для первого запуска](#первый-запуск).
4. Запустите приложение:

```sh
make up
```

Эта команда сама поднимет БД, применит миграции, соберёт и запустит API. Отдельно устанавливать Go или PostgreSQL для этого не нужно. После запуска контейнеры продолжат работать в фоне.

Проверьте результат:

```sh
docker compose ps
```

У сервисов `api` и `postgres` должен быть статус `healthy`. API будет доступен на `http://127.0.0.1:8080`. Примеры запросов с ключом находятся в разделе [«Запросы к API»](#запросы-к-api).

### Первый запуск

Создайте файл настроек:

```sh
cp .env.example .env
```

Сгенерируйте ключ:

```sh
openssl rand -hex 32
```

Команда выведет строку из 64 символов. Откройте `.env`, найдите `API_KEY=` и вставьте эту строку сразу после `=`, без пробелов. Остальные значения можно оставить как в примере. Сохраните файл и выполните `make up`.

Если `.env` уже заполнен, повторять эти шаги и менять ключ не нужно.

### Если запуск не удался

- `Cannot connect to the Docker daemon` — запустите Docker Desktop и повторите `make up`.
- Ошибка про `API_KEY` — проверьте, что в `.env` после `API_KEY=` записан ключ.
- `port is already allocated` — порт занят другим приложением. Укажите в `.env` свободный, например `POSTGRES_PORT=5433` для БД или `API_PORT=8081` для API, и повторите `make up`. При `API_PORT=8081` адрес API будет `http://127.0.0.1:8081`.

По умолчанию PostgreSQL публикуется на `127.0.0.1:5432`. Внутри Docker адрес БД всегда остаётся `postgres:5432`.

### Логи и остановка

```sh
make logs  # Посмотреть логи API; Ctrl+C закроет просмотр, сервис продолжит работать
make down  # Остановить контейнеры, сохранив данные БД
```

Данные хранятся в постоянном Docker-томе и остаются после повторного `make up`. Настройки `POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD` используются при первом создании БД: правка `.env` не меняет пароль уже существующей роли.

После смены API-ключа или других настроек выполните `make up` ещё раз. Compose пересоздаст API с новым окружением; `docker compose restart api` изменения `.env` не подхватит. Новый ключ также нужно передать клиентам. Рабочие ключи и `.env` в Git не добавляются.

Ожидание готовности ограничено 30 секундами. Если контейнеру нужно больше времени на запуск, увеличьте его:

```sh
make API_WAIT_TIMEOUT=60 up
```

## Запросы к API

Полный контракт находится в [OpenAPI](docs/backend/openapi.yaml).

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/info` | Создать угрозу, `201` |
| GET | `/info/{md5}` | Получить угрозу, `200` |
| PUT | `/info/{md5}` | Обновить угрозу, `200` |

Все три операции требуют заголовок `Authorization: Bearer <API_KEY>`. Для примеров ниже подставьте ключ из `.env` и адрес своего API:

```sh
export API_KEY='<ключ из .env>'
export API_URL=http://127.0.0.1:8080
```

Создание:

```sh
curl -i -X POST "$API_URL/info" \
  -H "Authorization: Bearer $API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"md5":"d41d8cd98f00b204e9800998ecf8427e","name":"Trojan.Win32.Generic","description":"Пример угрозы"}'
```

Чтение:

```sh
curl -i "$API_URL/info/d41d8cd98f00b204e9800998ecf8427e" \
  -H "Authorization: Bearer $API_KEY"
```

Обновление:

```sh
curl -i -X PUT "$API_URL/info/d41d8cd98f00b204e9800998ecf8427e" \
  -H "Authorization: Bearer $API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Trojan.Win32.Updated"}'
```

POST требует строковые `md5` и `name`, PUT — `name`. Поле `description` необязательно. PUT заменяет изменяемые поля целиком: если не передать `description`, старое описание удалится. Отсутствующая запись при этом не создаётся.

MD5 должен состоять из 32 hex-символов. Регистр не важен, в ответе хеш всегда записан в нижнем регистре. Пустые `name` и `description` допустимы, пробелы сохраняются. `null` и U+0000 в этих полях запрещены. Неизвестные поля игнорируются, даты назначает БД и возвращает в UTC.

Ошибки имеют общий формат:

```json
{"message":"Threat not found","details":""}
```

| Код | Когда возвращается |
| --- | --- |
| 400 | Неверный MD5, JSON, тип или размер тела запроса |
| 401 | Ключ отсутствует или не подходит |
| 404 | Запись или маршрут не найдены |
| 405 | Метод не поддерживается; допустимые методы указаны в `Allow` |
| 409 | Запись с таким MD5 уже есть |
| 429 | Превышен лимит запросов; время ожидания указано в `Retry-After` |
| 500 | Внутренняя ошибка без раскрытия деталей БД |

POST и PUT принимают один JSON-объект с `Content-Type: application/json`; разрешён `charset=utf-8`. HEAD возвращает `405` без тела. Проверка ключа выполняется до маршрутизации, поэтому запрос без ключа получит `401` даже на неизвестный путь. Ошибки разбора HTTP до обработчика и разрыв соединения не гарантируют JSON-ответа.

## Доступ и лимиты

Используется один API-ключ с одинаковым доступом к чтению и записи. Пользователей и ролей нет. Ключ должен содержать 32–256 символов `A–Z`, `a–z`, `0–9`, `_` или `-`.

Перед проверкой ключа работает token bucket по IP: по умолчанию доступны 20 запросов сразу, затем восстанавливаются 10 токенов в секунду. Неверные ключи тоже расходуют лимит. IP берётся из TCP-соединения; `Forwarded` и `X-Forwarded-For` не учитываются. Клиенты за одним NAT или reverse proxy делят общий лимит.

В памяти хранится не больше `HTTP_RATE_LIMIT_MAX_CLIENTS` адресов. Записи удаляются после пяти минут бездействия: очистка выполняется при запросах раз в минуту и при заполнении таблицы. Если места нет, новый IP получает `429` с `Retry-After: 60`. Лимиты действуют в пределах одного процесса и сбрасываются при его перезапуске.

В Compose порты опубликованы только на localhost. Для внешнего доступа нужен HTTPS, например через reverse proxy: сам API слушает обычный HTTP. Контейнер приложения работает от непривилегированного пользователя в `scratch`; CA bundle добавлен для TLS-подключений к PostgreSQL.

## Настройки

Приложение читает только переменные окружения через `cleanenv`. Compose загружает `.env` сам, локальный Go-процесс — нет. Значение по умолчанию используется только для отсутствующей переменной; явно пустое значение считается ошибкой. Все длительности должны быть положительными, например `500ms` или `5s`.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `API_KEY` | Обязательная | Bearer-ключ, формат описан выше |
| `LOG_LEVEL` | `INFO` | Уровень `slog`, включая значения вроде `DEBUG+2` |
| `HTTP_ADDR` | `127.0.0.1:8080` | Адрес сервера; порт `0` выбирает свободный порт |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` | Чтение заголовков |
| `HTTP_READ_TIMEOUT` | `10s` | Чтение запроса вместе с телом |
| `HTTP_WRITE_TIMEOUT` | `15s` | Запись ответа |
| `HTTP_IDLE_TIMEOUT` | `60s` | Ожидание следующего запроса в keep-alive соединении |
| `HTTP_SHUTDOWN_TIMEOUT` | `10s` | Время на завершение текущих запросов |
| `HTTP_MAX_BODY_BYTES` | `1048576` | Лимит тела POST/PUT в байтах, положительное `int64` |
| `HTTP_RATE_LIMIT_RPS` | `10` | Число восстанавливаемых токенов в секунду на IP |
| `HTTP_RATE_LIMIT_BURST` | `20` | Ёмкость bucket на IP |
| `HTTP_RATE_LIMIT_MAX_CLIENTS` | `10000` | Максимум хранимых IP |
| `POSTGRES_HOST` | `127.0.0.1` | Хост БД; IPv6 без квадратных скобок |
| `POSTGRES_PORT` | `5432` | Порт БД, от 1 до 65535 |
| `POSTGRES_DB` | `threats` | Имя базы |
| `POSTGRES_USER` | `threats` | Роль подключения |
| `POSTGRES_PASSWORD` | Обязательная | Пароль; пробелы не обрезаются |
| `POSTGRES_SSLMODE` | `disable` | `disable`, `allow`, `prefer`, `require`, `verify-ca`, `verify-full` |
| `POSTGRES_MAX_CONNS` | `10` | Максимальный размер пула |
| `POSTGRES_CONNECT_TIMEOUT` | `5s` | Подключение и общий бюджет запуска |
| `POSTGRES_OPERATION_TIMEOUT` | `5s` | Ожидание пула, выполнение SQL и чтение результата одной операции |

Размер пула и три числовые настройки rate limit принимают значения от 1 до 2147483647. Имена БД, роли и хоста должны быть непустыми. Ошибки конфигурации содержат имя переменной, но не её значение. Строка подключения собирается через `net/url`, поэтому спецсимволы в пароле не нужно экранировать вручную.

`API_PORT` — отдельная переменная Compose для публикации API на хосте, по умолчанию `8080`. В контейнере API всегда слушает `0.0.0.0:8080`, а PostgreSQL доступна ему по `postgres:5432`. `POSTGRES_PORT` в `.env` задаёт порт БД на хосте.

Таймаут операции БД начинается при входе в repository и не включает чтение HTTP-тела. Более ранний deadline родительского контекста имеет приоритет. Отмена запроса не гарантирует откат записи на сервере, поэтому автоматических повторов записи нет. `HTTP_WRITE_TIMEOUT` ограничивает отправку ответа отдельно: оставьте запас на чтение запроса и запись результата.

## Запуск без контейнера API

Нужен Go 1.27.3. БД и миграции можно подготовить через Compose:

```sh
make db-up
make migrate-up
```

Передайте приложению ключ, пароль и порт из своего `.env`. Например, если PostgreSQL опубликована на порту `5432`:

```sh
API_KEY='<ключ из .env>' \
POSTGRES_PASSWORD='<пароль из .env>' \
POSTGRES_PORT=5432 \
HTTP_ADDR=127.0.0.1:8081 \
make run
```

Здесь выбран порт `8081`, чтобы не пересекаться с API в Docker. `make build` собирает тот же сервис в `bin/api`. При первом запуске Go и инструментов разработки может потребоваться сеть для загрузки зависимостей.

## База и миграции

Схема описана в [SQL-миграции](migrations/000001_create_threats.up.sql).

| Поле `threats` | Тип | Условия |
| --- | --- | --- |
| `md5` | `text COLLATE "C"` | Первичный ключ; CHECK на 32 hex-символа в нижнем регистре |
| `name` | `text` | NOT NULL, пустая строка допустима |
| `description` | `text` | NULL означает отсутствие описания; пустая строка хранится отдельно |
| `created_at` | `timestamptz` | NOT NULL, назначается БД при создании и не меняется при PUT |
| `updated_at` | `timestamptz` | NOT NULL, назначается БД при создании и обновляется при PUT |

Индекс один — первичный ключ по MD5. Запись и обновление выполняются одним SQL-запросом с `RETURNING`. Дубликат определяется по ограничению `threats_pkey`; остальные ошибки БД сохраняют причину для `errors.Is/As`. При конкурентных обновлениях остаётся последняя успешная запись. `updated_at` не используется как версия и не гарантирует строгое возрастание.

```sh
make migrate-up       # Применить миграции
make migrate-version  # Посмотреть текущую версию
make db-shell         # Открыть psql
make migrate-down     # Откатить одну миграцию
```

Откат текущей миграции удаляет таблицу `threats` вместе с данными. Для изменения схемы добавляйте новую пару up/down, не редактируя уже применённые миграции.

При запуске бинарник проверяет только подключение через `Ping`. Схему и состояние миграций он не проверяет, DDL не выполняет. Если забыть применить миграции, процесс запустится, но бизнес-запрос вернёт `500`. В `make up` миграции выполняются до старта API, и ошибка мигратора останавливает запуск.

## Готовность и остановка

Команда `/api healthcheck` внутри контейнера обращается к `GET /readyz` и ожидает `200` с `{"status":"ready"}`. Этот маршрут доступен только прямому loopback-клиенту, не требует ключа и не расходует rate limit. Снаружи возвращается `404`.

Readiness проверяет доступность PostgreSQL, но не совместимость схемы. Бюджет проверки БД — меньшее из `POSTGRES_OPERATION_TIMEOUT` и `1s`, общий бюджет команды — `2s`. При недоступной БД маршрут возвращает `503`. Не проксируйте внешний доступ к `/readyz` через локальный reverse proxy: приложение увидит его как loopback-клиента.

По SIGINT или SIGTERM сервер перестаёт принимать новые соединения и ждёт текущие запросы до `HTTP_SHUTDOWN_TIMEOUT`. Их контексты не отменяются вместе с сигналом. Если время вышло, запросы отменяются, соединения закрываются принудительно, затем закрывается пул БД. Штатное завершение даёт exit code `0`, ошибка запуска или принудительная остановка по таймауту — `1`.

В Compose `stop_grace_period` равен `30s`. Если увеличиваете таймаут завершения приложения, увеличьте и это значение. Логи записываются в JSON через `slog`: запросы и события сервера — в stdout, фатальные ошибки — в stderr. Ключи, пароли, DSN и тела запросов не логируются.

## Устройство проекта

HTTP-обработчик разбирает запрос и вызывает `ThreatService`. Сервис проверяет предметные данные и обращается к интерфейсу `ThreatRepository`. Интерфейс находится в usecase, реализация — в PostgreSQL-адаптере. Domain и usecase не зависят от HTTP и SQL. Зависимости передаются через конструкторы в `internal/app`.

| Каталог | Что внутри |
| --- | --- |
| `cmd/api` | Точка входа, сигналы, exit code и команда healthcheck |
| `internal/app` | Сборка зависимостей и жизненный цикл сервера |
| `internal/config` | Чтение и проверка окружения |
| `internal/domain` | Модель угрозы, MD5 и предметные ошибки |
| `internal/usecase` | Сервис и интерфейс repository |
| `internal/repository/postgres` | Хранилище и сгенерированный пакет `dbgen` |
| `internal/transport/http` | Роутинг, JSON, авторизация, limiter и middleware |
| `db/queries` | SQL-запросы для sqlc |
| `migrations` | Миграции up/down |
| `tests/integration` | Проверки repository, usecase и HTTP с PostgreSQL |
| `tests/database` | Миграции и ограничения БД |
| `tests/runtime` | Проверки настоящего бинарника |
| `tests/compose` | Запуск через Compose и сохранность тома |
| `tests/testutil` | Общие helpers для Docker-тестов |

Контракты типов и методов можно посмотреть через `go doc`, например:

```sh
go doc ./internal/usecase ThreatRepository
```

## Проверки и генерация

| Команда | Что делает |
| --- | --- |
| `make check` | Форматирование, vet и unit-тесты |
| `go test -race ./...` | Unit-тесты с race detector |
| `make lint` | golangci-lint |
| `make test-integration` | Integration-тесты с настоящей PostgreSQL |
| `make test-db` | Миграции, dirty-состояние и ограничения таблицы |
| `make test-runtime` | HTTP, сигналы и ошибки бинарника; Dockerfile, Compose и сохранность данных |
| `make build` | Сборка `bin/api` |
| `make docker-build` | Сборка Docker-образа |

Docker-тесты написаны на Go и отделены тегами `integration` и `e2e`. Testcontainers поднимает временную PostgreSQL со случайным портом и реквизитами. Миграции применяет одноразовый контейнер `golang-migrate`. Compose smoke test использует отдельный проект и том. После прогона тесты удаляют только свои ресурсы; внешний `TEST_DATABASE_URL` не используется. `make test-repository` оставлен как алиас `make test-integration`.

После изменения [OpenAPI](docs/backend/openapi.yaml) или SQL-запросов обновите сгенерированный код:

```sh
make generate
# Или отдельно:
make generate-http
make generate-sql
```

Схему для sqlc задают миграции. DTO создаёт oapi-codegen, а роутинг и проверка JSON остаются в HTTP-адаптере. Сгенерированные файлы хранятся в Git и не редактируются вручную. Версии генераторов и линтера закреплены в Makefile; обычная сборка их не запускает.

[CI](.github/workflows/ci.yaml) проверяет генерацию, форматирование, сборку, vet, тесты с `-race` и линтер. Docker-проверки запускаются отдельной задачей.
